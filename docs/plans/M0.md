## 1. Decisions (confirmed 2026-10-08)

Each of these changes or adds to the spec. T17 writes them into SPEC v0.6.

| # | Decision | What it means and why |
|---|---|---|
| D1 | **pnpm 12** (12.10.1), pinned in `packageManager` | pnpm 10 gets security fixes only until 2027-04-30; pnpm 12 has no end date. pnpm 12 reads only auth/registry settings from `.npmrc`, so all pnpm settings live in `pnpm-workspace.yaml`. **Risk:** pnpm's `SECURITY.md` still calls the Rust port "not production ready", while the pnpm 12 announcement calls it stable. T00 tested it on Windows on 2026-10-08 and it worked: install, build and hot reload all pass. **Corepack caveat:** Corepack 0.34 can't run pnpm 12, so a machine that ran `corepack enable` must run `corepack disable` (see T00). The cause is in Corepack, not Windows, so expect it on any OS where Corepack is on; only the Windows case was tested. Fallback if pnpm 12 ever fails: pnpm 11.28, which has the same settings and lockfile, supported until 2027-04-30; not needed so far |
| D2 | **E: is reformatted from exFAT to NTFS before T00** (you do this; the path `E:\shopblok-starter` stays) | exFAT has no shortcuts (symlinks), no file permissions, no journal (crash protection) and no hard links. Large exFAT drives also default to 128 KB blocks, so hundreds of thousands of small library files would take far more space than their real size. NTFS has all of these. Every exFAT workaround from the first draft is dropped: copy-instead-of-link installs, injected workspace packages, symlink checks, and the exFAT CI job |
| D3 | **Apps read shared packages' source directly** | Each `@shopblok/*` package exports TypeScript source and has no build step. pnpm links it into each app, Next compiles it, and edits hot-reload. Security and hosting costs are the same as the build-then-copy alternative |
| D4 | **Pin `next@16.4.0` exactly**, replacing "≥ 16.3.6". Renovate opens a PR for each new release, and CI tests it before merge | 16.3.6 fixes GHSA-vcvr-r3jv-pc5j but not the six advisories of 2026-09-30 (fixed in 16.3.8). Two of those apply here: a draft-mode leak through `'use cache'` deduplication (GHSA-3w37-wq28-93x7) and a cache leak across root-param values (GHSA-h694-7cp9-m8p3). 16.4.0 contains every fix, and OSV lists no vulnerabilities for it |
| D5 | **Pin TypeScript 5.9.3** | TS 7.0 (npm `latest`) has no JS API until 7.1. Medusa's CLI uses `ts-node`, and `medusa build` calls `ts.createProgram`. typescript-eslint needs TS < 6.1, and Payload's tsconfig uses `baseUrl`, which TS 7 rejects |
| D6 | **pnpm's normal (isolated) layout.** The `node-linker=hoisted` line is dropped | That line was only needed for exFAT (D2). Normal mode is what dtc-starter uses. | D7 | **Seeding runs through `medusa exec` scripts.** `seed-markets.ts` runs in every environment; `seed-demo-catalog.ts` runs in development only. dtc-starter's `migration-scripts/initial-data-seed.ts` is removed | dtc-starter seeds inside `medusa db:migrate`, which also runs in Railway's predeploy step, so demo products would reach production. Its seed is also hard-wired to one EUR region with different countries |
| D8 | **One Medusa locale per language**, stored in `markets`: `el→el-GR`, `de→de-DE`, `fr→fr-FR`, `en→en-US`. `de-CH` and `fr-CH` shoppers see the German and French translations | Medusa's Locale table holds 51 BCP 47 codes such as `el-GR` and `de-CH`. It has no bare `el`, and no `el-CY`. The spec's store locales `en, de, fr, el` don't exist as written |
| D9 | **Payload uses saved migrations everywhere.** `push` is off by default; `PAYLOAD_DB_PUSH=true` turns it on for schema experiments | `payload migrate` prompts when dev push has touched the database, which would make `pnpm bootstrap` interactive and non-deterministic. | D10 | **The market map lives in Payload's `markets` global** (the editable part in M0). `proxy.ts` reads it through `getMarketMap()`, with a 30 s in-process cache. | D12 | **M0 Payload schema is minimal:** `users`, `integrations`, `media`, a `pages` stub (localized title/slug, drafts) and a `markets` subset | Enough for the wiring, S1 and S3. Everything else is M4 |

| D15 | **Host ports are 15432 for Postgres, 6380 for Redis and 7701 for Meilisearch.** The containers keep 5432, 6379 and 7700 inside (raised by T00, confirmed 2026-10-08; Postgres moved from 5433 to 15432 in the PR 3 review) | Your machine already runs another project's containers on 5432, 6379 and 7700, so `docker compose up` failed there. T13's preflight also checks that the service on each port belongs to this project's compose stack, not just that something answers |

Process only: no spec change |
| D17 | **Whoever uses the starter picks their regions, currencies and languages in one place each, and they work at once, with no code change outside it** (Stephanos, 2026-10-09) | A US, Brazilian, Greek or Mongolian shop must be able to open a market easily and find it working: regions, prices in its currency, its language, search indexing and price filtering in **every** selected currency (not only EUR and USD). M0 has one list per app, and they must agree: the backend's `apps/backend/src/config/markets.ts` (currencies, regions, Medusa locales, store name; **done in T08's PR**, and the search index reads the same list, so `min_price_<currency>` exists for every store currency; verified with Brazil and Mongolia, SETUP.md "Backend decisions from T07 (done in T08)") and the storefront's market map (the `markets` global and its fixture, T10). ## 3. Skills and references

The three skills come from `github.com/medusajs/medusa-agent-skills` (read at commit `066132d1c20550cc36c0122e83970eaefe9a2bfd`). Install the `medusa-dev` and `ecommerce-storefront` plugins locally so `/…` invocation works.

**In the cloud (D16), plugins don't install.** The setup script in [CLOUD.md](../CLOUD.md) downloads the same repo at the same commit to `/opt/medusa-agent-skills`, and sessions read the files listed below from there: `plugins/medusa-dev/skills/<skill>/…` and `plugins/ecommerce-storefront/skills/storefront-best-practices/…`. The same script also fetches dtc-starter (`/opt/dtc-starter`) and Payload's templates (`/opt/payload-templates/{blank,with-postgres,ecommerce}`), because a running session can't download other repos (C0). The Medusa docs MCP server isn't available there either, so use the `docs.medusajs.com` pages, which the environment allows. Don't count on that server locally: on 2026-10-08 it refused an unauthenticated request (HTTP 401), and the plugin's connection to it failed in a local session (HTTP 402).

The tasks use these short names:

| Short | Skill | References (exact file names) |
|---|---|---|
| **BWM** | `/medusa-dev:building-with-medusa` | `SKILL.md`; `reference/{custom-modules, data-models, workflows, api-routes, authentication, querying-data, module-links, subscribers-and-events, workflow-hooks, scheduled-jobs, error-handling, frontend-integration, troubleshooting}.md` |
| **BS** | `/medusa-dev:building-storefronts` | `SKILL.md`; `references/frontend-integration.md` |
| **SBP** | `/ecommerce-storefront:storefront-best-practices` | `SKILL.md`; `reference/{connecting-to-backend, medusa, design, seo, mobile-responsiveness}.md`; `reference/components/country-selector.md`; `reference/layouts/*.md` |
| **CMD** | `medusa-dev` command skills | `skills/new-user`, `skills/db-generate`, `skills/db-migrate` |

**Where the skills have nothing.** They don't cover `allowFields`, seeding with `medusa exec`, the Translation or Search Modules, Next 16 caching or `proxy.ts`, Payload, pnpm, or integration tests. For those, use the official docs listed in each task and the Medusa docs MCP (`https://docs.medusajs.com/mcp`). The highest Medusa version the skills mention is 2.17.3.

**Rules from the skills that apply across tasks:**
- Load the reference before writing the code it covers.
- Every Medusa write goes Module → Workflow → Route, using core-flows workflows in seeds too.
- Routes use only GET, POST and DELETE.
- Generate and run migrations as separate steps (`db:generate`, then `db:migrate`).
- Workflow composition functions are synchronous: no async/await, conditionals or loops; use `when()`/`transform()` instead.
- Never multiply or divide prices by 100.
- A task is done only when its build passes, plus `medusa lint` for the backend.
- Always use the JS SDK, never raw `fetch()`. Always send the publishable key. Never hard-code regions or products.

**Where we deliberately differ from the skills** (record in SETUP.md):
- Data comes from a server-first DAL. React Query is only for client interactivity, from M3.
- The region comes from the URL and `proxy.ts`, not from `localStorage`.
- We cache with `'use cache'`, `cacheLife` and `cacheTag`, not the `revalidate` export: that export is a build error under Cache Components.
- We pin exact versions; the skills use `@latest`.
- We run Medusa commands with `pnpm --filter @shopblok/backend exec medusa …`.
- The skill's store-route curl example leaves out the `x-publishable-api-key` header; always send it.

### S2 · Search Module: per-locale indexing

**Question:** How do we index and query products per locale with Medusa 2.21's Search Module, for both the keyless default (`search-postgres`) and the M6 Meilisearch provider? And can a language added in settings become searchable without code?

**Known going in (verified in 2.21.2):**
- Search documents carry no locale, and the ingestion context is just `{ container, index }`.
- `/store/search` ignores `req.locale`. It accepts `search_options.locales` and passes it to the provider, but both first-party providers **throw** on it.
- The Postgres provider takes a single `language` option and can't be registered twice.
- The one documented approach is per-locale fields (`title_fr`, …), filled in `transform` by re-querying with `query.graph(…, { locale })`.
- The Translation Module emits `translation.created/updated/deleted` with payload `{ id }`. Using these to trigger reindexing is our inference, not documented.
- Index fields are defined statically with `search.define`, while locales are data.
- Prices are not locale data: since T08 the index holds a `min_price_<currency>` set for every currency the store sells in (D17), so S2 has no price work left.

**Candidates:**
- **A: per-locale fields in one logical index**, generated from store `supported_locales` at startup. A new locale needs a worker restart and a reindex.
- **B: one physical index per locale** inside the custom Meilisearch provider. The provider splits each document into per-locale documents and picks the index from `search_options.locales`. Postgres would use A.
- **A′: one multilingual index.** A single searchable field concatenates every locale's text, facets use IDs (labels come from translations), and hits are shown translated by re-fetching with `x-medusa-locale`. This is also the fallback.

**Setup:**
- On `spike/s2-search-locales`, build a minimal prototype `meilisearch-search` provider (upsert, delete, search; extends `AbstractSearchProviderService`) and the index-definition variants.
- Seed the product "Linen shirt" with `el-GR` "Λινό πουκάμισο", `de-DE` "Leinenhemd" and `fr-FR` "Chemise en lin".
- Tests are `@medusajs/test-utils` `medusaIntegrationTestRunner` specs in `apps/backend/integration-tests/http/search-locale.spec.ts`, run against both providers.

**Tests:**

| # | Test | Required for PASS |
|---|---|---|
| T1 | `q=πουκάμισο` with locale `el-GR` hits; `Leinenhemd`/`de-DE`, `chemise`/`fr-FR` and `shirt`/`en-US` hit too | both providers |
| T2 | Accents and tonos ignored: `πουκαμισο` matches (`unaccent`) | both providers |
| T3 | Isolation: `Leinenhemd` with `el-GR` doesn't hit, or ranks below native-language hits | Meilisearch (B); informational for Postgres |
| T4 | Freshness: `updateTranslationsWorkflow` on the `el-GR` title is searchable within 10 s in worker mode, through a `translation.updated` → product `resolve_ids` mapping | both providers |
| T5 | Facets: category facet labels in the active locale, or IDs that the storefront labels | both providers |
| T6 | Hits come back translated: one extra `sdk.store.product.list({ id: [...] })` with `x-medusa-locale` returns translated titles and prices | both providers |
| T7 | Dynamic locale: add `it-IT` to `supported_locales` plus one translation; it becomes searchable with at most a worker restart and a reindex, and no code change | both providers (needed for SPEC G7) |
| T8 | Cost: index size and reindex time for 1,000 products × 4 locales, for each candidate | recorded |
| T9 | D17: a language outside en/el/de/fr works: `pt-BR` ("Camisa de linho") and `mn-MN` ("Маалинган цамц", Cyrillic) titles are found by their own words. Record which Postgres text-search configuration the provider uses for them (PostgreSQL has no Mongolian one, so expect `simple` plus the trigram index) | both providers; the Mongolian result is recorded, and may be "found by trigram only" |

**PASS** (keep the spec's "one index per locale") = T1, T2, T4, T5, T6 and T7 pass with B on Meilisearch, and T1, T2, T4, T6 and T7 pass with A or A′ on Postgres.

**FAIL → fallback:**
- **A′ on both providers:** one index, multilingual search text, facets on IDs, translated display through hydration.
- **If T4 fails** (no event path): add a scheduled `reindex-products` job plus the existing admin reindex button.
- **If `search_options.locales` doesn't reach the provider:** B is impossible, so A′ applies.

**Handoff:**
- The ADR picks the index design.
- M3 implements the index definition (the PLP depends on it).
- M6 implements the production Meilisearch provider.
- The prototype stays on the spike branch.

### S3 · Payload locale preloading with `filterAvailableLocales`

**Question:** Does preloading about 42 locales (D17) stay cheap? Does `filterAvailableLocales`, driven by the `markets` global, restrict the admin correctly and dynamically? And what is the runbook for a language outside the list?

**Known going in (verified in 3.90.2):**
- **Signature:** `({ locales: Locale[]; req }) => Locale[] | Promise<Locale[]>`. It works on locale objects.
- **Scope:** it filters only the admin locale selector, the version view, and publishing under the experimental `localizeStatus`. It does **not** filter the REST or Local API.
- **Call count:** it runs at least twice per admin page load and isn't recomputed on client navigation; the docs suggest `router.refresh` after changes.
- **The crash is fixed:** the "admin crashes if `defaultLocale` is filtered out" bug (#11598) was fixed in 3.28 (PR #11614). The admin now falls back to the first allowed locale. Returning `[]` is still an edge case to avoid.
- **Storage:** Postgres keeps every locale code in one `_locales` enum, plus a `<table>_locales` table per localized table. Adding or removing a locale changes the enum, so production needs `migrate:create` + `migrate`. Reads load every locale row that has content.

**Setup:** the T09 config with the full preload list (about 42 languages: the EU's 24 and every language Medusa has a locale for, D17) and the `markets`-driven filter. Two copies of the same database: one configured with the full list, one with 4.

**Tests:**

| # | Test | Pass condition |
|---|---|---|
| L1 | `payload migrate:create` with the full list (about 42 locales) generates the initial migration; `payload migrate` on an empty database exits 0 | both run; time recorded |
| L2 | `markets` enables `el` + `en`; the admin locale selector shows exactly those (Playwright) | exact match |
| L3 | Enable `de` in `markets`, then reload the page | `de` appears with no server restart |
| L4 | `markets` enables only `el` | selector shows `el` + `en` (forced); no error |
| L5 | `markets` is empty (fresh database) | selector shows `en`; the filter never returns `[]` |
| L6 | Open the admin with `?locale=fr` while `fr` is disabled | redirected to an allowed locale, no crash |
| L7 | Memoization | at most 1 `markets` read per admin request (counter in `req.context`) |
| L8 | `GET /api/pages?locale=fr` while `fr` is disabled | returns 200. This confirms the filter is admin-only, so the ADR must say the storefront enforces markets |
| L9 | Performance: a page with localized fields filled in 4 locales; 100 × `findByID` and the admin edit-view load, full-list config vs 4-locale config | full-list p50 ≤ 1.2 × the 4-locale p50 |
| L10 | Runbook: add a locale outside the list (e.g. `ga`) to a database that has content, then `migrate:create` + `migrate` | the migration applies cleanly; the steps go into SETUP.md |
| L11 | Removing a locale that has content | record the behaviour; expected to fail, which leads to an "add-only" policy |

**PASS** = L1–L8 and L10 pass, and L9 is within budget.

**FAIL → fallback:**
- **L2–L6 fail:** a custom admin locale-selector component that reads `markets`. Keep `filterAvailableLocales` as a safety net.
- **L9 fails or L1 is painful:** preload only each brand's planned languages (a per-brand constant in `src/payload/locales.ts`) and rely on the L10 runbook. That ends D17's "no migration to add a language" for Payload (the runbook is then the price of a new language), so the ADR says so and D17 is amended.
- **L11 shows removal breaks:** document "locales are add-only". Disabling happens in `markets`, never in the config.
