# M0 plan: Foundation

**Status:** draft for review, not started · **Date:** 2026-10-08 · **Spec:** [SPEC.md](../SPEC.md) v0.5, §17.1

> **M0 (SPEC §17.1):** monorepo, compose, backend from dtc-starter, Next 16.4 + Payload 3.90 shell, market resolution + proxy rewrite, `bootstrap`/`doctor`, CI.
> **Spikes:** Cache Components × Payload admin; Search Module per-locale indexing; Payload locale preloading with `filterAvailableLocales`.
> **Done when:** everything boots wired together with no keys, and the spike ADRs are written.

Paths in this plan are relative to the repo root (`E:\shopblok-starter` locally). Every version and API below was checked against the official docs, the npm registry and the upstream repos on 2026-10-08 (sources in §10).

## 1. Decisions to confirm before starting

The plan uses these defaults. Each one changes or adds to the spec, so please confirm or change it.

| # | Decision | Why |
|---|---|---|
| D1 | **Pin pnpm 10.34.6** through `packageManager`. Put the linker settings in both `.npmrc` and `pnpm-workspace.yaml` | pnpm 11+ no longer reads `node-linker` from `.npmrc` (it keeps only auth/registry settings there), and pnpm 12 is a Rust rewrite with stricter config. pnpm 10.6+ reads both files; `pnpm-workspace.yaml` wins |
| D2 | **exFAT needs more than `node-linker=hoisted`**. Also set `package-import-method=copy`, `injectWorkspacePackages: true` and `dedupeInjectedDeps: false` | With the hoisted linker, `workspace:*` packages are still symlinked, with a junction as fallback, and exFAT supports neither (libuv reports `EISDIR`). Injected workspace packages are real copies. `symlink=false` is worse: workspace packages silently don't get linked at all |
| D3 | **Shared packages export TypeScript source.** Apps resolve `@shopblok/*` to `packages/*/src` through tsconfig `paths`, and Turbopack applies these as aliases | In pnpm 10, injected copies don't update while a watcher is running, so without aliases edits in `packages/ui` wouldn't hot-reload on E:. The installed copy is still there for Node tooling |
| D4 | **Pin `next@16.4.0` exactly.** This replaces "≥ 16.3.6" | 16.3.6 fixes GHSA-vcvr-r3jv-pc5j but not the six advisories of 2026-09-30 (fixed in 16.3.8). Two of those apply here: a draft-mode leak through `'use cache'` deduplication (GHSA-3w37-wq28-93x7) and a cache leak across root-param values (GHSA-h694-7cp9-m8p3). 16.4.0 contains every fix, and OSV lists no vulnerabilities for it |
| D5 | **Pin TypeScript 5.9.3** | TS 7.0 (npm `latest`) has no JS API until 7.1. Medusa's CLI uses `ts-node`, and `medusa build` calls `ts.createProgram`. typescript-eslint needs TS < 6.1, and Payload's tsconfig uses `baseUrl`, which TS 7 rejects |
| D6 | **React 19.3.0 lives at the root.** The Medusa admin's React 18.3.1 nests under `apps/backend` | Under the hoisted linker, packages listed in the root manifest take the root `node_modules`. The admin's Vite config dedupes `react` from the backend project. A check script enforces this (T03) |
| D7 | **Seeding runs through `medusa exec` scripts** (`seed-markets.ts`, `seed-demo-catalog.ts`). dtc-starter's `migration-scripts/initial-data-seed.ts` is removed | dtc-starter seeds inside `medusa db:migrate`, so seeding would also run in Railway's predeploy step. Its seed is also hard-wired to one EUR region with different countries |
| D8 | **Medusa locales are region-tagged.** Each content language maps to one Medusa locale, stored in `markets`: `el→el-GR`, `de→de-DE`, `fr→fr-FR`, `en→en-US`. `de-CH` and `fr-CH` reuse the German and French translations | Medusa's Locale table holds 51 BCP 47 codes such as `el-GR` and `de-CH`. It has no bare `el`, and no `el-CY`. The spec's store locales `en, de, fr, el` don't exist as written |
| D9 | **Payload `push` is off by default.** Dev uses committed migrations too; `PAYLOAD_DB_PUSH=true` turns push on for schema experiments | `payload migrate` prompts when dev push has touched the database, which would make `pnpm bootstrap` interactive and non-deterministic |
| D10 | **The market map lives in Payload's `markets` global** (the editable part in M0). `proxy.ts` reads it through `getMarketMap()`, with a short in-process TTL cache. Region IDs come from Medusa at render time | Markets are data (Principle 10). The M4 sync fills the read-only part of the global later. Proxies always run on Node.js in Next 16, so they can use the Local API. Fallback in T10 |
| D11 | **Root `compose.yaml` `include`s `infra/docker-compose.yml`** | Plain `docker compose up` works from the repo root, and the spec's file location stays |
| D12 | **M0 Payload schema is minimal:** `users`, `integrations`, `media`, a `pages` stub (localized title/slug, drafts) and a `markets` subset | Enough for the wiring, S1 and S3. Everything else is M4 |
| D13 | **Spike code lives on `spike/*` branches.** Only ADRs, the tests that encode a decision, and config changes merge into `main` | Keeps prototype code (for example a Meilisearch provider) out of the foundation |
| D14 | **Backend tests stay on Jest** (Medusa's `@medusajs/test-utils`, as in dtc-starter). Storefront and packages use Vitest | Medusa's test runner is Jest-based. SPEC §14 says Vitest for unit tests, so this needs a note there |

## 3. Skills and references

The three skills come from `github.com/medusajs/medusa-agent-skills` (read at commit `066132d1c20550cc36c0122e83970eaefe9a2bfd`). Install the `medusa-dev` and `ecommerce-storefront` plugins locally so `/…` invocation works. The tasks use these short names:

| Short | Skill | References (exact file names) |
|---|---|---|
| **BWM** | `/medusa-dev:building-with-medusa` | `SKILL.md`; `reference/{custom-modules, data-models, workflows, api-routes, authentication, querying-data, module-links, subscribers-and-events, workflow-hooks, scheduled-jobs, error-handling, frontend-integration, troubleshooting}.md` |
| **BS** | `/medusa-dev:building-storefronts` | `SKILL.md`; `references/frontend-integration.md` |
| **SBP** | `/ecommerce-storefront:storefront-best-practices` | `SKILL.md`; `reference/{connecting-to-backend, medusa, design, seo, mobile-responsiveness}.md`; `reference/components/country-selector.md`; `reference/layouts/*.md` |
| **CMD** | `medusa-dev` command skills | `skills/new-user`, `skills/db-generate`, `skills/db-migrate` |

**Where the skills have nothing.** They don't cover `allowFields`, seeding with `medusa exec`, the Translation or Search Modules, Next 16 caching or `proxy.ts`, Payload, pnpm, or integration tests. For those, use the official docs listed in each task and the Medusa docs MCP (`https://docs.medusajs.com/mcp`). The highest Medusa version the skills mention is 2.17.3.

**Rules from the skills that apply across tasks:**
- Load the reference before writing the code it covers.
- Every Medusa write goes Module → Workflow → Route, using core-flows workflows in seeds too.
- Routes use only GET, POST and DELETE.
- Generate and run migrations as separate steps (`db:generate`, then `db:migrate`).
- Workflow composition functions are synchronous: no async/await, conditionals or loops; use `when()`/`transform()` instead.
- Never multiply or divide prices by 100.
- A task is done only when its build passes, plus `medusa lint` for the backend.
- Always use the JS SDK, never raw `fetch()`. Always send the publishable key. Never hard-code regions or products.

**Where we deliberately differ from the skills** (record in SETUP.md):
- Data comes from a server-first DAL. React Query is only for client interactivity, from M3.
- The region comes from the URL and `proxy.ts`, not from `localStorage`.
- We cache with `'use cache'`, `cacheLife` and `cacheTag`, not the `revalidate` export: that export is a build error under Cache Components.
- We pin exact versions; the skills use `@latest`.
- We run Medusa commands with `pnpm --filter @shopblok/backend exec medusa …`.
- The skill's store-route curl example leaves out the `x-publishable-api-key` header; always send it.

          └─ T11 proxy + [market] root → T12 DAL + wiring page
              └─ T13 bootstrap → T14 doctor → T15 root scripts → T16 CI → T17 docs, ADRs, spec v0.6

- **S1 gates T12.** The DAL's cache wrapper and `next.config.ts` depend on its outcome.

- **Timeboxes:** S1 1 day, S2 2 days, S3 1 day. If a timebox runs out, the spike ends as FAIL and we take its fallback.

### T00 · exFAT preflight (on `E:`, about 1 hour)

**Goal:** prove the toolchain works on exFAT before building on it. pnpm maintainers say exFAT can't hold symlinks, and a Next.js discussion (#77912) reports `next build` (webpack) failing on exFAT with `EISDIR … readlink`. Nobody has tested Turbopack.

**Touches:** a throwaway folder `E:\shopblok-exfat-probe` (not committed).

**Docs:** pnpm settings (`nodeLinker`, `packageImportMethod`, `injectWorkspacePackages`, `dedupeInjectedDeps`); Next `turbopack.root`.

**Steps:**
1. Create a minimal workspace: the root `.npmrc` and `pnpm-workspace.yaml` from T01, plus `packages/probe` (exports a TS constant) and `apps/web` (`next@16.4.0`, imports `@shopblok/probe` through tsconfig `paths` per D3, and as a `workspace:*` dependency).
2. Run `pnpm install`, `pnpm --filter web build` (Turbopack), and `pnpm --filter web dev`. Edit `packages/probe/src/index.ts` and watch for HMR.
3. Install `@medusajs/medusa@2.21.2` in a second app and run `medusa --version`. The real `medusa build` check happens after T05.

**Verify:**
- `pnpm install` exits 0.
- PowerShell prints nothing for `Get-ChildItem -Recurse -Force -Attributes ReparsePoint node_modules, apps\*\node_modules`.
- `node -e "console.log(require('fs').lstatSync('node_modules/@shopblok/probe').isSymbolicLink())"` prints `false`.
- `pnpm-lock.yaml` shows `file:packages/probe` (injected).
- `next build` exits 0; the HMR edit appears within 2 s.

**If it fails:** move development to NTFS, a ReFS Dev Drive, or WSL2 (all of which remove every exFAT constraint). The repo config stays exFAT-safe either way. Record the result in SETUP.md.

### T01 · Workspace and package-manager config

**Touches:** `.npmrc`, `pnpm-workspace.yaml`, `package.json`, `.nvmrc`, `.gitignore`, `.editorconfig`, `turbo.json`, `compose.yaml` (D11, filled in T04).

**Skills/docs:** BWM `SKILL.md` (validation section); pnpm settings and pnpm 10 changelog; Turborepo `turbo.json` reference.

**Steps:**
1. Commit `.npmrc` **before the first install**:
   ```ini
   node-linker=hoisted
   package-import-method=copy
   ```
2. Create `pnpm-workspace.yaml`:
   ```yaml
   packages: ["apps/*", "packages/*", "scripts"]
   nodeLinker: hoisted
   packageImportMethod: copy
   injectWorkspacePackages: true
   dedupeInjectedDeps: false
   hoistWorkspacePackages: false   # no-op on pnpm 10; stops pnpm 11.28+/12.7+ from creating symlinks
   syncInjectedDepsAfterScripts: [build]
   autoInstallPeers: true
   minimumReleaseAge: 1440
   allowBuilds: { "@medusajs/telemetry": true, esbuild: true, "@swc/core": true, sharp: true, unrs-resolver: true }
   overrides: {}                    # overrides go here, never under package.json#pnpm
   ```
   Confirm the `allowBuilds` list against `pnpm ignored-builds` after the first real install.
3. Root `package.json`:
   - `"private": true`
   - `"packageManager": "pnpm@10.34.6+sha512.<hash>"`
   - `"engines": { "node": ">=22.22.0 <25", "pnpm": ">=10.34.6 <11" }`
   - devDependencies `turbo@2.11.7`, `typescript@5.9.3`, `react@19.3.0`, `react-dom@19.3.0` (D6), `prettier@3`
   - scripts `dev`, `build`, `typecheck`, `lint`, `test`, `bootstrap`, `doctor`, `infra:up`, `infra:down`, `infra:reset`, `check:workspace`, filled in T15
4. Create `turbo.json`:
   - `build`: depends on `^build`; inputs `$TURBO_DEFAULT$` and `.env*`; outputs `.next/**`, `!.next/cache/**`, `.medusa/server/**`, `dist/**`.
   - `dev`: `cache: false`, `persistent: true`.
   - `typecheck`, `lint`, `test`.
   - `db:migrate` and `seed`: `cache: false`.
5. `.gitignore`: `node_modules`, `.next`, `.medusa`, `.turbo`, `.env`, `.env.*` but not `.env.example`, `apps/storefront/media/` (local uploads), Playwright output.

**Verify:**
- `pnpm -v` prints `10.34.6`.
- `pnpm config get node-linker` prints `hoisted`.
- `pnpm install` on the empty workspace exits 0.
- `pnpm exec turbo --version` prints `2.11.7`.

### S1 · Cache Components × Payload admin

**Question:** Can `cacheComponents: true` (and `partialPrefetching: true`) stay on with the embedded Payload 3.90.2 admin on Next 16.4.0, and do Payload Local API reads work inside `'use cache'` with tag revalidation?

**Known going in:**
- Payload ≥ 3.81 wraps its admin root layout in `<Suspense>` when Cache Components is on (PR #16020). Payload's docs say "full compatibility is not guaranteed".
- Known limitations:
  - a gray flash on hard refresh;
  - admin 404s return HTTP 200;
  - Activity can break Playwright selectors.
- Open issues:
  - #18065: Next 16.3+ dev error "encountered the unstable value Date.now() while prerendering";
  - login fails with Instant Navigations + `partialPrefetching` (PR #16020 thread);
  - #16270: media selection forces a full reload.
- The community workaround **W1** adds `export const instant = false` + `await connection()` to the generated `admin/[[...segments]]/page.tsx`.
- Next side:
  - `updateTag`/`refresh()` work only in Server Actions. Payload hooks run in its REST route handler, so they must use `revalidateTag(tag, 'max' | { expire: 0 })`.
  - #99741 (open): Partial Prerendering pages lose their cache after `next start` restarts. That affects self-hosting only.

**Setup:** the T09 app plus a test route `(storefront)/[market]/spike-cache` that reads `pages` through the Local API inside `'use cache'` + `cacheTag('pages:<locale>')`. A `pages` `afterChange` hook calls `revalidateTag('pages:<locale>', 'max')`. The draft-aware variant uses `draftMode()`.

**Test matrix:** {`next dev`, `next build && next start`} × {`partialPrefetching` on, off} × {no workaround, W1}.

**PASS** requires all of the following in one matrix column, in both dev and start:
1. `next build` exits 0. No route has a "blocking route" or "Uncached data was accessed outside of `<Suspense>`" error, or a sync-I/O prerender error.
2. The admin Playwright suite passes with zero browser-console errors or hydration warnings:
   - first-user creation, login and logout;
   - create, edit and publish a page in 2 locales, then switch locales;
   - upload an image to `media` and select it without a full reload;
   - paginate the list view.
3. `GET /api/pages` returns 200. Admin 404s returning 200 are accepted, because `/admin` is disallowed and noindex; the ADR records this.
4. Cache behaviour:
   - the second request to `spike-cache` is served from cache, measured with an instrumentation counter;
   - after an admin edit, fresh content appears within 2 requests (`'max'` is stale-while-revalidate);
   - `revalidateTag(tag, { expire: 0 })` from a route handler gives fresh content on the next request.
5. **Draft isolation** (regression test for GHSA-3w37-wq28-93x7): 200 concurrent requests, mixed between draft-cookie and public. No public response contains the draft marker.
6. The market home builds as partially prerendered (`◐` in the build output) with a streamed dynamic hole.

**FAIL** = no column passes within the timebox.

**Outcome → action:**
- **PASS with no workaround and `partialPrefetching` on:** keep the spec as is.
- **PASS only with W1 and/or `partialPrefetching: false`:**
  - Adopt that column. The ADR lists the exact edits to the generated file.
  - `check-workspace.ts` asserts the W1 edit is still there, since the file isn't regenerated automatically but an upgrade could replace it.
  - Renovate PRs for `payload` or `next` run the admin suite.
  - If partial prefetching is the culprit, prefer `export const prefetch = 'force-disabled'` on the admin route over turning it off globally.
- **FAIL → fallback:**
  - Set `cacheComponents: false` and `partialPrefetching` off.
  - `src/lib/cache.ts` switches to `unstable_cache(fn, keyParts, { tags, revalidate })`, which still works in 16.4.
  - Revalidation uses `revalidateTag(tag, 'max')`; cart, checkout and account render dynamically.
  - SPEC §8.3 gets rewritten.
  - Splitting Payload into its own Next app is **not** a fallback within M0: it would reverse the [Decided] embedding and needs your call.

### S2 · Search Module: per-locale indexing

**Question:** How do we index and query products per locale with Medusa 2.21's Search Module, for both the keyless default (`search-postgres`) and the M6 Meilisearch provider? And can a language added in settings become searchable without code?

**Known going in (verified in 2.21.2):**
- Search documents carry no locale, and the ingestion context is just `{ container, index }`.
- `/store/search` ignores `req.locale`. It accepts `search_options.locales` and passes it to the provider, but both first-party providers **throw** on it.
- The Postgres provider takes a single `language` option and can't be registered twice.
- The one documented approach is per-locale fields (`title_fr`, …), filled in `transform` by re-querying with `query.graph(…, { locale })`.
- The Translation Module emits `translation.created/updated/deleted` with payload `{ id }`. Using these to trigger reindexing is our inference, not documented.
- Index fields are defined statically with `search.define`, while locales are data.

**Candidates:**
- **A: per-locale fields in one logical index**, generated from store `supported_locales` at startup. A new locale needs a worker restart and a reindex.
- **B: one physical index per locale** inside the custom Meilisearch provider. The provider splits each document into per-locale documents and picks the index from `search_options.locales`. Postgres would use A.
- **A′: one multilingual index.** A single searchable field concatenates every locale's text, facets use IDs (labels come from translations), and hits are shown translated by re-fetching with `x-medusa-locale`. This is also the fallback.

**Setup:**
- On `spike/s2-search-locales`, build a minimal prototype `meilisearch-search` provider (upsert, delete, search; extends `AbstractSearchProviderService`) and the index-definition variants.
- Seed the product "Linen shirt" with `el-GR` "Λινό πουκάμισο", `de-DE` "Leinenhemd" and `fr-FR` "Chemise en lin".
- Tests are `@medusajs/test-utils` `medusaIntegrationTestRunner` specs in `apps/backend/integration-tests/http/search-locale.spec.ts`, run against both providers.

**Tests:**

| # | Test | Required for PASS |
|---|---|---|
| T1 | `q=πουκάμισο` with locale `el-GR` hits; `Leinenhemd`/`de-DE`, `chemise`/`fr-FR` and `shirt`/`en-US` hit too | both providers |
| T2 | Accents and tonos ignored: `πουκαμισο` matches (`unaccent`) | both providers |
| T3 | Isolation: `Leinenhemd` with `el-GR` doesn't hit, or ranks below native-language hits | Meilisearch (B); informational for Postgres |
| T4 | Freshness: `updateTranslationsWorkflow` on the `el-GR` title is searchable within 10 s in worker mode, through a `translation.updated` → product `resolve_ids` mapping | both providers |
| T5 | Facets: category facet labels in the active locale, or IDs that the storefront labels | both providers |
| T6 | Hits come back translated: one extra `sdk.store.product.list({ id: [...] })` with `x-medusa-locale` returns translated titles and prices | both providers |
| T7 | Dynamic locale: add `it-IT` to `supported_locales` plus one translation; it becomes searchable with at most a worker restart and a reindex, and no code change | both providers (needed for SPEC G7) |
| T8 | Cost: index size and reindex time for 1,000 products × 4 locales, for each candidate | recorded |

**PASS** (keep the spec's "one index per locale") = T1, T2, T4, T5, T6 and T7 pass with B on Meilisearch, and T1, T2, T4, T6 and T7 pass with A or A′ on Postgres.

**FAIL → fallback:**
- **A′ on both providers:** one index, multilingual search text, facets on IDs, translated display through hydration.
- **If T4 fails** (no event path): add a scheduled `reindex-products` job plus the existing admin reindex button.
- **If `search_options.locales` doesn't reach the provider:** B is impossible, so A′ applies.

**Handoff:**
- The ADR picks the index design.
- M3 implements the index definition (the PLP depends on it).
- M6 implements the production Meilisearch provider.
- The prototype stays on the spike branch.

### S3 · Payload locale preloading with `filterAvailableLocales`

**Question:** Does preloading about 35 locales stay cheap? Does `filterAvailableLocales`, driven by the `markets` global, restrict the admin correctly and dynamically? And what is the runbook for a language outside the list?

**Known going in (verified in 3.90.2):**
- **Signature:** `({ locales: Locale[]; req }) => Locale[] | Promise<Locale[]>`. It works on locale objects.
- **Scope:** it filters only the admin locale selector, the version view, and publishing under the experimental `localizeStatus`. It does **not** filter the REST or Local API.
- **Call count:** it runs at least twice per admin page load and isn't recomputed on client navigation; the docs suggest `router.refresh` after changes.
- **The crash is fixed:** the "admin crashes if `defaultLocale` is filtered out" bug (#11598) was fixed in 3.28 (PR #11614). The admin now falls back to the first allowed locale. Returning `[]` is still an edge case to avoid.
- **Storage:** Postgres keeps every locale code in one `_locales` enum, plus a `<table>_locales` table per localized table. Adding or removing a locale changes the enum, so production needs `migrate:create` + `migrate`. Reads load every locale row that has content.

**Setup:** the T09 config with the full preload list and the `markets`-driven filter. Two copies of the same database: one configured with 35 locales, one with 4.

**Tests:**

| # | Test | Pass condition |
|---|---|---|
| L1 | `payload migrate:create` with 35 locales generates the initial migration; `payload migrate` on an empty database exits 0 | both run; time recorded |
| L2 | `markets` enables `el` + `en`; the admin locale selector shows exactly those (Playwright) | exact match |
| L3 | Enable `de` in `markets`, then reload the page | `de` appears with no server restart |
| L4 | `markets` enables only `el` | selector shows `el` + `en` (forced); no error |
| L5 | `markets` is empty (fresh database) | selector shows `en`; the filter never returns `[]` |
| L6 | Open the admin with `?locale=fr` while `fr` is disabled | redirected to an allowed locale, no crash |
| L7 | Memoization | at most 1 `markets` read per admin request (counter in `req.context`) |
| L8 | `GET /api/pages?locale=fr` while `fr` is disabled | returns 200. This confirms the filter is admin-only, so the ADR must say the storefront enforces markets |
| L9 | Performance: a page with localized fields filled in 4 locales; 100 × `findByID` and the admin edit-view load, 35-locale config vs 4-locale config | 35-locale p50 ≤ 1.2 × the 4-locale p50 |
| L10 | Runbook: add a locale outside the list (e.g. `ga`) to a database that has content, then `migrate:create` + `migrate` | the migration applies cleanly; the steps go into SETUP.md |
| L11 | Removing a locale that has content | record the behaviour; expected to fail, which leads to an "add-only" policy |

**PASS** = L1–L8 and L10 pass, and L9 is within budget.

**FAIL → fallback:**
- **L2–L6 fail:** a custom admin locale-selector component that reads `markets`. Keep `filterAvailableLocales` as a safety net.
- **L9 fails or L1 is painful:** preload only each brand's planned languages (a per-brand constant in `src/payload/locales.ts`) and rely on the L10 runbook.
- **L11 shows removal breaks:** document "locales are add-only". Disabling happens in `markets`, never in the config.

## 8. Spec findings to apply in v0.6

Found while checking the spec against the docs. T17 applies the ones you confirm.

1. **§3 / §11.1:** the Next pin moves from "≥ 16.3.6" to **16.4.0**, with the reason (D4).
2. **§3 / §4:** pnpm 10.34.6 pinned; the exFAT settings (D1–D3); TypeScript 5.9.3.
3. **§5 / §6.1 seeding:** seeds run through `medusa exec`, not a migration script (D7). The dtc-starter backend has **no email-verification code** (only its storefront does), so M3 must add:
   - `http.authVerificationsPerActor`;
   - a subscriber on `auth.verification_requested`;
   - `notification-local` on the email channel;
   - `admin.storefrontUrl`.
4. **§5 / §8.5:** Medusa store locales are `en-US`, `el-GR`, `de-DE` and `fr-FR`, not `en/de/fr/el`. Add the language → Medusa locale mapping (D8).
5. **§6.1 caching row:** the Caching Module *can* run without Redis via `in_memory: { enable: true }`. We still gate it on Redis on purpose.
6. **§6.2 / §8.5 / §10.5 search:** "one index per locale" depends on S2. The Search Module has no locale support at all (see S2's "Known going in").
7. **§7.1 localization:**
   - The `defaultLocale` crash was fixed in 3.28. Keep `en` because it's the fallback target.
   - The filter must never return `[]`.
   - `filterAvailableLocales` filters only the admin UI, so the storefront and access control enforce markets.
8. **§7.1 setup:**
   - `withPayload` adds `Vary`/`Critical-CH: Sec-CH-Prefers-Color-Scheme`, `Accept-CH` and `X-Powered-By` to **every** route. Handle in M7 (CDN caching, `poweredByHeader: false` intent).
   - `devBundleServerPackages: false`.
   - `turbopack.root` at the repo root.
   - Windows Sass `loadPaths`.
9. **§7.7 / §8.3:**
   - `updateTag`/`refresh()` are Server-Action-only. Payload hooks use `revalidateTag(tag, 'max')`, which the spec already says.
   - Don't copy Payload's website-template `dynamic`/`revalidate` exports.
10. **§8.3:** depends on S1's outcome.
11. **§8.5 / M3:** `[market]` is a `next/root-params` root param. next-intl 4.14 reads it in `getRequestConfig` (`setRequestLocale` is deprecated). Route handlers and server actions pass `locale` explicitly. Don't use next-intl's `Link`/`createNavigation`.
12. **§3 "Why not fork":** the deprecation of nextjs-starter-medusa (in the README since 2026-04-23) is confirmed; the GitHub "archived" flag wasn't checked.
13. **§14:** backend tests use Jest (D14). CI uses compose instead of `services:`.
