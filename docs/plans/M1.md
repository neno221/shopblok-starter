**Goal:** Style Dictionary (D26) builds `tokens.css` from the two token files, light only, and the build enforces SPEC §13's contrast gate.

## 6. Spikes

### S4 · Where catalog data lives, and the status of a backend outage (SPEC §8.1)

**Question:** can the indexable catalog pages put their Medusa data in the static shell (`cached()`, and `notFound()` before any `Suspense`), so that a backend outage serves the last good page or a 5xx and never a 200 error page, a missing product is a real 404, and CI's builds without a backend still pass? And does a `/next/status` route give an uptime monitor an honest answer?

**Timebox:** one day. **Branch:** the session's own, with the prototype in one commit that the next commit removes, as in S1 to S3; only ADR 0004, the tests that carry its decision and SETUP.md stay in the tree.

**Known going in:**
- T12 (SETUP.md, T12 item 2): a streamed part's failure gives status 200 and the error state; a page that blocks gives 200 and Next's bare error page. The default then was "leave it as it is".
- W2's second run saw it again: the first request after `pnpm dev`, while Medusa was still starting.
- Next 16.4's docs: a streamed response starts with 200, so a status check has to run before the body streams; with Cache Components, `generateStaticParams` must return at least one param (`empty-generate-static-params`).
- `cached()` (`lib/cache.ts`): a `use cache` call that throws caches nothing, and the page recovers once the backend is back (T12).
- D10's precedent: the market map falls back to fixtures in development and while `next build` runs, never in production.
- SPEC §12: `notFound()` before any `Suspense` boundary, so that a missing page is a real 404.

**Setup:** a throwaway page `(storefront)/[market]/spike-product/[handle]` in two variants: **(A)** the data in a `Suspense` part, as the wiring page does; **(B)** the data in the shell through `cached()`, with a `cacheLife` like the catalog's will be, and `generateStaticParams` from Medusa with a build stand-in when no backend is configured. Plus **(C)**, a `/next/status` route. `next build && next start`, with the stack up and `pnpm bootstrap` run; Medusa is stopped and started by PID.

**Tests:**

| # | Test | B (or C) passes when |
|---|---|---|
| O1 | A prerendered handle, Medusa up | 200 with the product |
| O2 | O1's URL with Medusa stopped, before and after the `revalidate` time | 200 with the last good product, never the error state; a warning in the log |
| O3 | A handle never rendered, Medusa stopped | a 5xx; record which, the body, and that nothing was cached |
| O4 | An unknown handle, Medusa up | 404 with the not-found page |
| O5 | O3's URL after Medusa is back | 200, with no restart |
| O6 | `pnpm build` in CI's state (no `.env`, no backend) | exit 0 with the stand-in; record what it prerenders |
| O7 | A build with `MEDUSA_BACKEND_URL` set and Medusa down | fails, naming Medusa (a deployment's build needs its backend, as D10's needs its database) |
| O8 | `/next/status` (C) | 200 with Medusa and Payload up; 503 within 3 s with Medusa stopped, with Payload's database stopped, and with Medusa hanging (a port that accepts and never answers); no internals in the body |
| O9 | The build output | B's route is `○` or `◐`, not `ƒ` |
| O10 | A, again, for the ADR's table | 200 and the error state with Medusa stopped (T12's result) |

**PASS** (D36's default holds) = O1 to O7 and O9 pass for B, and O8 for C.

**FAIL → fallback:** A for every page, as today, plus C; the ADR says which of O1 to O9 failed. SPEC §12's "`notFound()` before any `Suspense` boundary" then cannot hold for catalog pages, and a missing product becomes a soft 404 (status 200). The ADR states that, together with whether a `noindex` in the error state survives streaming (measured then as O11), and you decide.

**Handoff:** ADR 0004 records D36 on a PASS, or your decision after a FAIL. M3 builds the home, PDP and PLP to it, and `/next/status` with the first catalog page; M4 does the same for CMS pages; M7 points the monitors at `/next/status`.
